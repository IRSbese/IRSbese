# Чек-лист проверки защиты production-настроек (Negative Testing)

Проверка устойчивости конфигурации приложения в production-окружении к небезопасным параметрам, значениям по умолчанию и попыткам обхода ограничений при редактировании.

---

## 1. Негативные сценарии при инициализации (Startup Validation)

Приложение в production-режиме (`ENV=production`) должно принудительно завершать запуск с ошибкой конфигурации (`ImproperlyConfigured` / `ValidationError`), если обнаружены следующие состояния:

| Категория | Негативный сценарий (Input) | Ожидаемый результат | Статус |
| :--- | :--- | :--- | :--- |
| **DEBUG-режим** | Установлено `DEBUG=True` (или `"1"`, `"true"`) при `ENV=production` | Отказ запуска; логирование критической ошибки конфигурации | [ ] |
| **Demo-режим** | Установлено `DEMO_MODE=True` в production-окружении | Отказ запуска либо принудительное отключение демо-авторизации и тестовых данных | [ ] |
| **Пустой `SECRET_KEY`** | Передана пустая строка `""`, пробелы `"   "` или `None` | Ошибка валидации при старте; запуск заблокирован | [ ] |
| **Слабый `SECRET_KEY`** | Передан ключ короче 32–50 символов или с низкой энтропией (например, `"a" * 64`) | Ошибка валидации при старте; запуск заблокирован | [ ] |
| **Дефолтный `SECRET_KEY`** | Передано значение из шаблона (`django-insecure-...`, `changeme`, `secret`) | Ошибка валидации при старте; запуск заблокирован | [ ] |
| **Небезопасные Cookies** | `SESSION_COOKIE_SECURE=False` или `CSRF_COOKIE_SECURE=False` | Ошибка запуска либо принудительная перезапись в `True` | [ ] |
| **Доступ к Cookies из JS** | `SESSION_COOKIE_HTTPONLY=False` | Ошибка запуска либо принудительная перезапись в `True` | [ ] |
| **Политика SameSite** | `SESSION_COOKIE_SAMESITE='None'` при `SESSION_COOKIE_SECURE=False` | Отказ запуска из-за несовместимости атрибутов безопасности | [ ] |
| **Отсутствие `.env`** | Запуск без файла `.env` и без системных переменных окружения (проверка fallback-значений в коде) | Приложение не использует захардкоженные пароли/ключи по умолчанию и требует явной передачи секретов | [ ] |

---

## 2. Проверка редактирования настроек и попыток обхода (API / Admin)

Если в системе предусмотрено динамическое изменение настроек через админ-панель или API-эндпоинты:

### 2.1. Допустимое редактирование (Позитивный сценарий)
- [ ] **Изменение разрешенных параметров:** обновление бизнес-настроек (название площадки, лимиты пагинации, контактные данные) проходит успешно (`200 OK`).
- [ ] **Изоляция системных флагов:** после сохранения разрешенных полей критические параметры (`DEBUG`, `SECRET_KEY`, `SECURE_COOKIES`) остаются неизменными.

### 2.2. Попытки обхода через изменение отдельных полей (Bypass)
- [ ] **Частичное обновление (`PATCH`):** отправка запроса только с одним запрещенным полем (например, `{"DEBUG": true}` или `{"session_cookie_secure": false}`) отклоняется (`400 Bad Request` / `403 Forbidden`) или поле игнорируется (`read_only`).
- [ ] **Подмена типов данных:** попытка передать строковые/числовые эквиваленты вместо булевых (`{"DEBUG": "1"}`, `{"DEMO_MODE": 1}`) не активирует небезопасный режим.
- [ ] **Сброс в `null`:** передача `{"SECRET_KEY": null}` не приводит к откату на небезопасное значение по умолчанию из кода.
- [ ] **Повторное включение Demo-режима:** попытка активировать `DEMO_MODE` через API после успешного запуска в production блокируется.

### 2.3. Контроль доступа (Privilege Escalation)
- [ ] **Неавторизованный пользователь:** запрос к эндпоинтам настроек возвращает `401 Unauthorized`.
- [ ] **Обычный пользователь / Продавец:** попытка чтения или изменения системных настроек возвращает `403 Forbidden`.

## 3. Автоматизированная проверка перед деплоем (CI/CD)

Для проектов на базе Django добавить в pipeline проверку конфигурации:

```bash
python manage.py check --deploy --fail-level WARNING
```

**Критерий прохождения:** команда завершается с кодом `0`, предупреждения уровня `security.W*` (связанные с `DEBUG`, `SECRET_KEY`, `SSL` и `Cookies`) отсутствуют.
